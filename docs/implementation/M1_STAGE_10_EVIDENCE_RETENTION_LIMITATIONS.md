# Stage 10 evidence retention: quarantine correction, canonical NO-GO

This mutable slice is **not approved for canonical publication, deployment, acceptance or Stage 10 closure**. No host/CT200, production, CI, key provisioning or historical evidence changes were made. Findings need independent adjudication; this document does not close them.

## Implemented containment and exact guarantees

- Retention now writes only beneath `<outputRoot>/quarantine/<bundleName>`. Schema v2 requires `retentionClass: QUARANTINE` and `privacyStatus: SCANNER_ONLY_REQUIRES_INDEPENDENT_REVIEW`. Unknown options, including caller-provided privacy approvals or purported authenticated pins, fail before filesystem I/O. There is no canonical publication/acceptance mode or API in this module. A caller can still copy files elsewhere outside this module; namespace separation is not OS access control.
- Returned verification describes an **observed mutable quarantine snapshot**, not trusted provenance or stable storage. It always reports `provenanceStatus: CALLER_DIGEST_NOT_AUTHENTICATED`. Caller-supplied expected receipt hashes remain consistency checks only. A substituted receipt plus substituted local hash can still enter quarantine; the test explicitly demonstrates that it does not acquire authenticated status.
- Every absolute root is walked from an open `/` descriptor one component at a time with `O_DIRECTORY | O_NOFOLLOW`. Relative reads similarly open each parent from the preceding descriptor. Linux `/proc/self/fd/<fd>/<single-component>` provides descriptor-anchored lookup; no attacker-controlled intermediate pathname is reused after a check. Directory enumeration, exclusive writes and staging creation use held descriptors too. The promotion helper inherits the already-open quarantine descriptor instead of reopening its path. Regular-file reads use `O_NOFOLLOW | O_NONBLOCK`, require a single-link regular bounded file and bound the read itself against concurrent growth.
- `renameat2(RENAME_NOREPLACE)` is the only quarantine name-promotion primitive. There is no ordinary-rename fallback. No cooperative locks or check-then-act destination checks are used. Existing directory, file and symlink destinations survive non-cooperating collision attempts unmodified. Unavailable no-replace support fails closed.
- The exact validated staging snapshot is hashed before promotion and checked again afterward. Promoted directory identity must match the held staging descriptor. These detect the tested one-shot staging-byte mutations and staging-name substitutions. **They do not prevent a same-UID attacker from modifying/restoring bytes around checks or modifying bytes after return.**
- No recursive pathname cleanup or lock removal is attempted. A hostile process could replace those names. Failed partial or rejected promoted attempts remain in quarantine for independently controlled disposal. Do not treat a visible non-dot name as successful retention; consume only a successful result and remember even that result is not durable authentication. No crash durability/fsync guarantee is made.

`bundleSha256` is SHA-256 of UTF-8 `JSON.stringify` of an ordered array: the index row `{path:"index.json",bytes,sha256}`, the index's sourceReceipt row, then its ordered log rows. Index bytes are themselves hashed exactly, including whitespace. This is an application-specific snapshot digest, not a signature, an independent receipt pin, or an immutable-object guarantee. The returned path is informational: an attacker can rename its ancestors after the anchored operation. Re-opened paths must be reverified.

## Required canonical acceptance design — not implemented or qualified

Canonical acceptance must run in an independently administered process/storage domain unavailable to the producer UID. Its code, interpreter, dependencies, configuration, public-key trust roots, credentials, process memory and destination ancestors must not be writable, replaceable or inspectable through producer access. A separate process with the same UID and the same writable dependencies is insufficient. Use a dedicated service UID with independently protected deployment and no producer ptrace/capability/credential access, or an independently administered authenticated remote service. This requires authorized provisioning beyond this local slice; no launch flag, signed self-assertion, owned directory or generated fixture is substituted for that boundary.

1. **Independent receipt pin:** obtain a strictly allowlisted, domain-separated authenticated envelope from a separately controlled receipt authority, not a producer-supplied key or adjacent digest file. Bind protocol/policy version, authority identity/key ID, candidate ID, artifact SHA-256, receipt SHA-256, issuance/expiry and replay identity. Authority key allowlists, role separation, revocation and freshness come from the protected service policy. Verify with an approved signature implementation/authenticated channel. A producer cannot replace authority keys, choose a verification callback, override the clock or redefine the expected candidate/artifact. Missing, stale, revoked, unsigned, unknown-field or wrong-binding pins deny acceptance.
2. **Freeze exact candidate bytes:** the independent writer snapshots quarantine into its own private staging/storage domain using descriptor-anchored no-follow reads and bounded verification. It checks the authenticated candidate/artifact/receipt binding and computes the exact snapshot digest there. Never check a mutable producer path and subsequently publish that path. Same-UID process and pathname controls must be demonstrated against an actual non-cooperating producer process, not assumed from mode bits.
3. **Independent privacy decision:** a separately authorized privacy reviewer assesses every receipt/log byte in that frozen snapshot. Its authenticated, domain-separated envelope binds candidate, artifact, receipt digest, exact bundle digest/immutable object version, policy version, classification, reviewer identity, issuance/expiry and an explicit APPROVE/REJECT decision. Scanner output is not this decision. Redaction creates new bytes, a new digest and a new review; the old approval cannot carry forward. Missing, stale, mismatched, revoked or unauthenticated decisions deny acceptance. Receipt and privacy roles must not be granted merely because one key verifies.
4. **Enforced acceptance:** only the protected writer can create the canonical namespace. It verifies both authorities against its protected policy, rechecks the digest of its own immutable snapshot and promotes that snapshot with actual no-replace semantics. It must provide authenticated readback of the exact immutable object/version and rejection evidence for substitution, freshness, replay, identity and privacy failures. Producer access to canonical files, accepted status or trust configuration must be denied by the actual OS/service boundary.

This design is a prerequisite, not implemented authentication. There are intentionally no fixture keys, boolean approval escape hatches, caller-defined verifiers or synthetic independence claims in this retention slice.
