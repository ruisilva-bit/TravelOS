# CT200 DEVELOPMENT database-only backup producer — review candidate

This is source for review, **not an installed or qualified operator, backup receipt, complete restore point, or Stage 10 GO**. It is not a transport or retention manager. No CT200 action was performed by this contribution.

The fixed root invocation is `/usr/bin/python3 -I /usr/local/lib/travelos/stage10-backup/stage10-ct200-backup-operator.py` with no arguments. Its stdout is binary CMS ciphertext only; stderr contains only a generic failure marker. Caller must treat a nonzero exit, broken stream, process loss or missing independently verified readback as an unknown/failed transfer, never as a backup success. A receiving process must enforce the reviewed off-instance protected store, no-replace publication, digest/readback, retention and reconciliation separately. Do not connect stdout directly to a terminal. No off-instance transmission is implemented here.

Installation requires independent review and separate approval. The fixed installation directory and all ancestors must be root-owned and not group/other writable; the three sibling native/encryption/process modules are pinned to the source hashes embedded in the operator. The existing identity checker under `/usr/local/lib/travelos/stage10-identity` is pinned separately. On each invocation root runs that fixed isolated CLI's `check` and requires VERIFIED before dropping all supplementary groups and switching permanently to the dedicated `travelos_backup` UID/GID. Native tools are fixed PG18 pins. Public recipient PEM is read from the fixed protected path and pinned; no private key is read. Environment/import safety, root-installed source integrity, identity-checker integrity, source file hashes and execution boundary need independent review prior to installation.

`/run/travelos-stage10-backup` must already exist as mode 0700 owned by `travelos_backup`, have safe ancestry, reside on tmpfs, and have 144 MiB free. Swap must be disabled; otherwise plaintext from tmpfs or process memory could spill to disk. Core dumps are disabled. The native helper collects at most 128 MiB of WAL-inclusive tar into memory and verifies the native manifest and WAL in the private tmpfs. It then compresses in memory and fails closed if compressed bytes exceed the existing encryption adapter's 8 MiB limit. No truncation is accepted. Actual CT200 compressibility is unknown; a large or incompressible cluster can fail despite a successful native backup. Memory and tmpfs capacity, timeout/rate impact, swap state and crash cleanup must be checked before any authorized run.

Ciphertext is AES-256-GCM CMS to the independently pinned recipient. Encryption and native verification do not prove a restorable database or authenticate external metadata. No storage-object capture, coordinated database/object cutoff, signed restore manifest, release/config/secret-reference coverage, protected retention scheduler, post-cutoff deletion reconciliation, isolated target restore, RPO/RTO or complete disaster-recovery evidence is provided. All remain separate gates under `docs/DEPLOYMENT_MODEL.md` and ADR-014.

Local verification: `test-stage10-ct200-backup-operator.py` covers composition order, bounds and failure gating. Existing synthetic PG18 fixture was additionally exercised by invoking the operator pipeline on its real produced archive, using the real native verifier and real ephemeral CMS encrypt/decrypt; this is not a CT200 identity/privileged-entry test. The existing fixture also checks WAL/manifest tamper rejection and isolated clone startup. The privileged installed entry, its root preflight, private staging provisioning, the full transport and CT200 operation remain untested.
