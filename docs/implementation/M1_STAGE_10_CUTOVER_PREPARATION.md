## Candidate and operational gaps

`tooling/deployment/stage10-operator.sudoers.in` is the existing versioned candidate grant; `stage10-cutover-preparation.py` renders it with a constrained account name and lowercase SHA-256 entry digest and checks it with actual `visudo`. It grants only the fixed native entry with `validate` and `activate`; the latter goes through the existing mandatory signature guard. `validate` does not perform signature verification. This is a fragment, **not** a complete replacement policy: other sudo includes, aliases, groups, setuid/polkit, privileged scripts, service configuration and writable executables may grant bypasses. It must never be installed while broad `NOPASSWD: ALL` or unsigned activation remains effective.

The existing candidate cannot run migrations, restart services, backup, restore, service health or general diagnostic operations. Therefore this candidate does **not** yet preserve the full autonomous deployment/backup/diagnostic workflow and is not ready for installation. Do not paper over this by granting shell, interpreters, arbitrary systemctl, broad root, or the old unsigned activation helper. A future independently reviewed narrowly scoped implementation and end-to-end tests must supply each required operation and ensure signature verification precedes any candidate execution or migration. Preserve independent administrative access; do not perform destructive down migrations as a rollback.

## Disposable rehearsal and limitations

`test-stage10-cutover-preparation.py` executes five real local tests using a fresh `TMPDIR` subdirectory: renders and parses the candidate with `visudo`; rejects malicious account/digest inputs, invalid syntax and symlink target; performs a candidate file swap; and injects a post-swap exception and verifies the old bytes return. It rejects `/etc/sudoers` as a target. The rehearsal uses scratch files only, is not a privileged installer and is not a security boundary against a hostile concurrent local user. The swap test does not prove rollback of modes/ownership, whole sudo policy, crashes, power failures, or recovery of an unavailable sudo service. `visudo -cf` validates syntax, not effective permissions or complete host policy. No live sudo command authorization or actual CT200 least-privilege/continuity was demonstrated by these five tests.

## Local unprivileged probe prototype — incomplete

`stage10-operations-dispatcher.py` is **not integrated with the native host entry or sudo**, deliberately refuses direct root execution, and is not a privilege boundary. It implements fixed-unit read-only systemd activity checks, a fixed `service-report` adapter that returns sanitized per-unit active/unavailable results, fixed loopback HTTP liveness checks, and root-filesystem free-space reporting. The report accepts no unit arguments, invokes only fixed `systemctl is-active --quiet` commands with a clean environment and timeout, and reports nonzero on any failure; it does not distinguish inactive from unknown or prove readiness. `backup` explicitly returns `BACKUP_NOT_IMPLEMENTED`; migration, restart, and activation are rejected. Existing signature-guarded activation remains unchanged and separate; no claim of integration is made. These probes do not establish application readiness, a usable backup, or recovery. The prototype cannot preserve operational continuity by itself.

Its disposable local tests exercise real loopback HTTP success/failure and negative arguments, backup denial and unavailable status. They do **not** exercise effective sudo authorization, protected executables, actual service status or host permissions. A further implementation and an independently reviewed isolated effective-permissions rehearsal are still required. No expanded sudo grant is proposed here.

## Synthetic backup integrity staging — not database recovery

`stage10-backup-staging.py` is a separate unprivileged LOCAL adapter, not wired to sudo, the dispatcher, the host entry or activation. It accepts exactly `backup` or `restore`, no caller-supplied paths/commands, and reads only the fixed private, already-existing `/home/hermes/.hermes/cache/scratch/travelos-stage10-backup-preparation` directory: `source.bin` → `backup.bin` → `restored.bin`. It is for synthetic data only: never put customer, database or credential data there. It bounds payloads to 8 MiB, output to one small JSON object and execution to a 10-second alarm (kernel uninterruptible I/O is not a hard real-time guarantee). It rejects linked/non-regular inputs, linked parent components, unsafe directory ownership/mode, changes detected during reads, extra arguments and pre-existing outputs. It writes a mode-0600 temporary file, fsyncs it, publishes without replacement, fsyncs the directory, and compares exact published bytes; restore checks SHA-256 before publication. A crash/timeout after publication may leave an ambiguous output or temporary file; stop and inspect rather than automatically retry or overwrite. Checksums detect accidental corruption, not a malicious owner who can rewrite both payload and checksum. The private directory and its ancestors must be protected from hostile concurrent writers; this is not a privilege or adversarial same-user boundary.

No `pg_dump` or `pg_restore` command was found in the local PATH during preparation. Synthetic byte round trips do **not** demonstrate PostgreSQL dump validity, restore, migration compatibility, privacy reconciliation, encryption, retention or RPO/RTO. The dispatcher deliberately continues to report `BACKUP_NOT_IMPLEMENTED`; the signature activation guard is unchanged. Before any real qualification, separately authorize an isolated pinned PostgreSQL environment and fixed protected database/credential and dump/restore command policy; establish consistent custom-format dump, restricted encrypted storage, exact checksum/readback, fresh isolated restore with `--exit-on-error`, source/restore schema, migration-ledger and representative-data parity, successful packaged migration verification, probe teardown, measured RPO/RTO, automatic expiry, and ADR-014 deletion-interval coverage/reconciliation before any opening. Independently review credentials, authority, access controls, failure/timeout handling and effective permissions. No live data, CT access or production claim is authorized by this preparation.
